## 1. 背景与目标

一期（数据仓库，73 家上海餐厅）、二期（后端只读 API，已上线 `https://ai4food.635262140.xyz`）、三期（前端 SPA，已上线 GitHub Pages）均已落地。四期接入 LLM，把"静态数据集"升级为"可对话的美食助手"，并降低人类贡献门槛。

### 本期目标

1. **智能问答推荐**：`POST /api/ai/recommend` -- 自然语言提问（"上海陆家嘴适合商务宴请的粤菜"）-> 检索候选餐厅 -> LLM 生成结构化推荐。
2. **AI 辅助贡献**：`POST /api/ai/draft` -- 自然语言描述一家店 -> LLM 生成符合 schema 的餐厅 frontmatter 草稿（JSON），人工核对后落盘。
3. **前端接入 AI**：三期前端加"问 AI"入口，调 `/api/ai/recommend` 展示推荐结果；辅助贡献走 API 但落盘仍由人完成（本期不做自动 PR）。

### 不在本期范围（后续规划）

- **不做自动 PR / 自动写 `data/`**：AI 辅助贡献只生成草稿 JSON，不直接写文件、不开 PR。`data/` 仍只放人类核对过的数据（铁律）。
- **不做向量检索 / Vectorize**：数据量小（~70 条），用二期已有 `query.ts` 规则筛选 + LLM 重排足够；向量检索留给数据量到数百条以上时再评估。
- **不做多轮对话 / 会话记忆**：本期是单轮请求-响应，不维护对话历史（不引 Durable Object / KV 存会话）。
- **不做鉴权 / 配额系统**：复用 AI Gateway 自带限流（`eatornot` 网关 100/分钟）+ Workers AI postpaid 计费；不实现用户级 API key。
- **不做流式输出**：本期返回完整 JSON，不做 SSE/streaming（简化前端处理）。

## 2. 关键技术决定

| 维度 | 决定 | 理由 |
|------|------|------|
| LLM 提供方 | **Workers AI**（Cloudflare 账号内置） | 无需外部 API key；与 Worker 同账号同运行时，无跨域/地域问题；postpaid 按量计费 |
| 主力模型 | `@cf/qwen/qwen3-30b-a3b-fp8` | 通义千问，中文菜系理解可靠；MoE 架构每次只激活 3B 参数，推理快；成本低（$0.051/M 输入、$0.335/M 输出，约 29 neurons/次）。备选 `@cf/zai-org/glm-4.7-flash`（中文更强但略贵） |
| 网关 | **AI Gateway `eatornot`**（账号已有） | 限流 100/分钟、缓存 300s、自带日志；复用现有资源不新建 |
| 调用方式 | **AI binding** `env.AI.run(model, input, { gateway })` | Worker 原生 binding，类型安全；`gateway.id` 指定网关走缓存与限流 |
| 检索 | **规则筛选 + LLM 重排** | 复用二期 `query.ts` 纯函数按城市/菜系/价位/标签/关键词筛出候选集，再把候选集塞进 prompt 让 LLM 选+解释。数据量小无需向量 |
| 提示词工程 | 系统提示词约束 LLM 只用候选集、输出结构化 JSON | 防幻觉：明确告知"只能从给定的餐厅里选"，并要求 JSON schema 输出 |
| 代码位置 | `tools/src/server/ai/` 下新增，`hono.ts` 挂新路由 | 保持工具链单一包；AI 逻辑与查询逻辑分层 |
| 前端 | 三期 `frontend/` 加视图，`fetch` 调 `/api/ai/recommend` | 前端从"直读 index.json"扩展为"也调 AI API"；列表页数据源不变 |

### 为什么用 Workers AI 而非外部 LLM

1. **无地域限制**：外部 LLM（Gemini/OpenAI）在中国大陆或 Workers 边缘节点可能有访问限制（记忆：之前 Gemini 直连失败需走 Gateway 代理）。Workers AI 在 Cloudflare 网络内运行，无此问题。
2. **无 key 管理**：AI binding 是账号级授权，不需要在 Worker 配 secret key，也不怕 key 泄露。
3. **成本可控**：postpaid 按神经元计费，小流量近乎免费；AI Gateway 缓存还能命中重复提问。
4. **模型够用**：Qwen/GLM 中文能力足以应对"餐厅推荐"这种基于给定数据集的封闭式问答。

### 成本估算

Workers AI 每天 **10,000 Neurons 免费额度**（UTC 0 点重置），超出才 $0.011/千 Neurons。单次推荐请求约 3K 输入 + 500 输出 token：

- Qwen3-30b（主力）：约 29 neurons/次 → **每天免费约 345 次推荐**
- GLM-4.7-flash（备选）：约 36 neurons/次 → 每天免费约 280 次

对 AI4Food 的公开 demo 流量，几乎永远落在免费额度内，实际计费趋近于零。AI Gateway `eatornot` 还带 300s 缓存，重复提问直接命中缓存不产生 LLM 调用。

### 为什么不做向量检索

当前 73 家餐厅，全量塞进 prompt 也才 ~30KB 文本（name/cuisine/tags/address/notes/description 摘要），远小于 GLM 上下文窗口。规则筛选（按 city/cuisine/price/tag）先把候选缩到十几条，再让 LLM 选--比向量检索更精准（精确匹配枚举值）、更简单（无 Vectorize 绑定与索引重建）、可测试（纯函数）。

等到数据量到 500+ 条或需要语义模糊匹配（"氛围感小酒馆"这种无法用枚举筛的），再引入 Vectorize。

## 3. API 设计

### 3.1 端点

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/ai/recommend` | 智能问答推荐：自然语言提问 -> 推荐餐厅列表 |
| POST | `/api/ai/draft` | AI 辅助贡献：自然语言描述 -> 餐厅 frontmatter 草稿 JSON |

所有端点：
- 请求/响应 `application/json; charset=utf-8`
- 错误统一 `{"error": "<message>"}`，状态码语义化（400 参数错误 / 429 限流 / 502 LLM 失败 / 500）
- 不需要鉴权（复用 AI Gateway 限流）

### 3.2 `POST /api/ai/recommend`

**请求**：
```json
{
  "question": "上海陆家嘴适合商务宴请的粤菜，人均 200 左右",
  "city": "上海"           // 可选，默认从提问推断或全部
}
```

**响应**：
```json
{
  "answer": "推荐两家：...",
  "picks": [
    {
      "id": "cn-shanghai-xxx",
      "name": "...",
      "reason": "符合商务宴请氛围，粤菜，人均契合...",
      "score": 0.92
    }
  ],
  "candidates_considered": 12,
  "model": "@cf/zai-org/glm-4.7-flash"
}
```

**流程**：
1. 解析 `question`，用规则从提问中抽取筛选条件（城市/菜系/价位/标签关键词）。
2. 调二期 `applyQuery(entries, params)` 拿候选集；候选集为空则放宽（去掉最不重要的筛选项重试一次）。
3. 候选集（精简字段：id/name/cuisine/price_level/tags/address/notes/rating）+ 提问 -> prompt -> LLM。
4. LLM 返回结构化 JSON（picks + answer），后端校验 schema、补全 id 存在性，返回。

### 3.3 `POST /api/ai/draft`

**请求**：
```json
{
  "description": "静安寺附近一家新开的日料omakase，人均500，环境很日式，主厨从东京回来，招牌是季节性鱼生"
}
```

**响应**：
```json
{
  "draft": {
    "id": "cn-shanghai-<suggest-slug>",
    "name": "...",
    "city": "上海",
    "country": "cn",
    "cuisine": "日料",
    "price_level": 4,
    "status": "open",
    "tags": ["日料", "omakase", "静安寺", "商务宴请"],
    "address": "...",
    "notes": "...",
    "description": "# ...(markdown 草稿)"
  },
  "warnings": [
    "address 未提供，需人工补充",
    "phone 未提供，需人工补充"
  ],
  "model": "@cf/zai-org/glm-4.7-flash"
}
```

**约束**：
- LLM 只生成草稿 JSON，**不写文件**。前端展示草稿，用户核对后手动创建 md（走一期贡献流程）。
- 枚举字段（`cuisine`/`status`/`price_level`）必须在 `schema/enums.json` 取值范围内；LLM 输出后由后端校验，越界则置默认值并在 `warnings` 提示。
- `id` 生成 `{country}-{city拼音}-{slug}`，后端检查全局唯一性，冲突则加后缀。

### 3.4 错误处理

| 场景 | 状态码 | 响应 |
|------|--------|------|
| `question`/`description` 为空或超长 | 400 | `{"error":"question 必填且不超过 500 字"}` |
| LLM 调用失败（Workers AI 5xx） | 502 | `{"error":"AI 服务暂时不可用"}` |
| LLM 输出 JSON 解析失败 | 502 | `{"error":"AI 响应格式异常"}` |
| AI Gateway 限流 | 429 | `{"error":"请求过于频繁，稍后再试"}` |

### 4.1 LLM 调用封装（`llm.ts`）

```ts
export interface LlmInput {
  system: string
  user: string
  jsonMode: boolean  // 要求 LLM 返回 JSON
}
export interface LlmOutput {
  text: string
  model: string
}

// 抽象接口，便于测试 mock
export interface LlmClient {
  run(input: LlmInput): Promise<LlmOutput>
}

// Worker 实现：env.AI.run + gateway
export function createWorkerLlm(ai: Ai, gatewayId = 'eatornot'): LlmClient {
  return {
    async run(input) {
      const resp = await ai.run(MODEL, {
        messages: [
          { role: 'system', content: input.system },
          { role: 'user', content: input.user },
        ],
        // Workers AI 的 response_format / json 模式按模型支持情况传
      }, { gateway: { id: gatewayId, skipCache: false, cacheTtl: 300 } })
      return { text: String(resp.response ?? ''), model: MODEL }
    },
  }
}
```

`createApp(loader, llm?)` 第二参数可选（默认用 Worker LLM）；测试注入 mock LlmClient。这样 Hono app 与 LLM 运行时解耦，与二期的 loader 解耦模式一致。

### 4.2 规则检索（`retrieve.ts`）

纯函数，入参 `(question: string, entries: IndexEntry[])`，出参 `{ candidates: IndexEntry[], params: QueryParams }`。

从提问中抽取：
- **城市**：匹配 `entries` 里出现过的 `city` 值（中文精确匹配）
- **菜系**：匹配 `schema/enums.json` 的 cuisine 枚举值
- **价位**：正则匹配"人均 X"或"价位 X"-> 映射 price_level（粗略，可选）
- **关键词**：剩余文本作为 `q` 模糊匹配 name/tags/address

抽完调 `applyQuery(entries, params)`，候选集 > N 条时截断（避免 prompt 过长），< 1 条时逐级放宽筛选项。

### 4.3 提示词（`prompt.ts`）

**recommend 系统提示词**（约束防幻觉）：
```
你是美食推荐助手。只能从给定的候选餐厅中选择，禁止编造不在候选集里的餐厅。
用户会提一个问题，你需要：
1. 从候选餐厅里挑出最符合的 1-3 家
2. 对每家给出简短推荐理由（结合提问需求）
3. 给出一句总结性回答
返回 JSON：{"answer": string, "picks": [{"id": string, "reason": string, "score": number}]}
id 必须来自候选集；score 为 0-1 的相关度。
```

候选集以精简 JSON 数组塞进 user 消息。

## 10. 待确认/风险

1. **GLM-4.7-flash 的 JSON 模式支持**：需实测 `env.AI.run` 时该模型是否支持 `response_format: json`。若不支持，退化为提示词要求"只输出 JSON" + 后端正则提取。
2. **候选集 prompt 体积**：73 条全量塞 prompt 约 30KB，GLM 上下文够。但若后续数据增长，需在 `retrieve.ts` 里做更激进的截断（只取 top-N 相关）。设计已留截断参数。
3. **LLM 幻觉**：即便提示词约束，LLM 仍可能编造 id。后端必须校验 picks 的 id 存在于候选集，不存在的丢弃（不报错，降级返回剩余）。
4. **辅助贡献的 id 唯一性**：LLM 生成的 slug 可能与现有冲突，后端用 `check-unique` 逻辑校验，冲突则加数字后缀。
